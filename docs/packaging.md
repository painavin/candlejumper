# Packaging

Desktop via Tauri, Android via Capacitor — roadmap step 11.

## Status: configured, not built

**Neither shell has been built.** Building Tauri needs a Rust toolchain and
building Capacitor needs the Android SDK, and neither is installed in the
environment these files were written in. What's here is the configuration and the
scripts; the first person with the toolchains installed should expect to fix
something.

Two things are known to still be needed for Tauri, both of which need a binary
asset or a native SDK rather than code:

- **Icons.** `bundle` has no `icon` array, because there are no icon files —
  the whole project ships exactly one binary asset (a font). Run
  `npx tauri icon path/to/source.png` to generate the set, then add
  `"icon": ["icons/32x32.png", "icons/128x128.png", "icons/icon.icns", "icons/icon.ico"]`.
- **`Cargo.toml` and `src-tauri/src/main.rs`.** Generated by
  `npm create tauri-app` / `npx tauri init`, which wants a Rust toolchain
  present. Running `npx tauri init` in this directory will fill them in around
  the existing `tauri.conf.json` rather than replacing it.

## The one setting that isn't boilerplate

`app.security.csp` allows `blob:` in **both** `script-src` and `worker-src`:

```
script-src 'self' blob:; worker-src 'self' blob:
```

This is load-bearing, not permissive-by-default. The plugin sandbox works by
`import()`-ing a blob URL inside a Web Worker
(`src/plugins/worker/pluginWorker.ts`), which is the *only* mechanism available
for evaluating player-supplied source in a worker. A default-restrictive CSP
silently breaks every imported plugin — the worker loads, the import rejects, and
the host reports a plugin that "did not load" with no obvious cause.

Worth stating plainly because it looks like a security regression and isn't: the
blob is what keeps plugin code inside the worker, where there is no DOM, no
Tauri bridge, and no filesystem. Denying `blob:` wouldn't make plugins safer, it
would make them impossible — and the pressure would then be to run them on the
main thread, which is the actually-dangerous option.

`connect-src` also lists `https://query1.finance.yahoo.com` and `https://stooq.com`,
the two price providers. Those entries are **necessary but not sufficient**, which is the part
worth knowing before debugging it: the Tauri webview enforces CORS exactly as a
browser does, and Yahoo sends no `Access-Control-Allow-Origin` (Stooq's header is
unchecked), so a plain `fetch` from the page fails in the desktop shell too. The fix is to add
`@tauri-apps/plugin-http` and a second implementation of the transport port beside
[`platform/http/browser.ts`](../src/platform/http/browser.ts) — its `fetch`
performs the request in Rust, outside the browser engine, where no such rule
exists. Capacitor's equivalent is `CapacitorHttp`, enabled with
`plugins.CapacitorHttp.enabled: true`, which reroutes `window.fetch` through
native Android code and therefore needs no new transport at all. Both also want
both provider hosts in the plugin's own permission allowlist. See
[data-sources.md](./data-sources.md#cors-is-the-whole-difficulty).

## Android (Capacitor)

`capacitor.config.json` points at `dist/`, so `npm run build` then
`npx cap sync` is the loop. Two things to do at that point:

- **Add `@capacitor/haptics`** and swap the body of
  `src/platform/haptics/haptics.ts` for it. The interface is already the one the
  game calls; only that file changes, which is why `platform/` exists.
- Check `webDir` output has the worker chunk. Vite emits the plugin worker as its
  own entry, and a packager that only copies `index.html` plus its direct imports
  would leave the sandbox behind.

## Static hosting

Neither shell is required — the build is a plain static bundle and runs entirely
client-side. See the README's deployment section for Azure Static Web Apps.
