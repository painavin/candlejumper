# Audio Design

## Approach

The ask was music/sound "tied to up/down" price movement. Full adaptive
music generation is a rabbit hole — instead, use **sonification**: map data
to simple musical events layered over a static ambient bed. Three
independent channels, each with its own volume/mute config.

Each channel's *mechanism* (how it works) is fixed by the engine. Its
*content* (which loop, which scale, which stinger sounds) is supplied by
the currently selected **audio theme** — see [Audio themes](#audio-themes)
below — so the game can ship multiple moods (jolly, serious, ...) without
touching channel logic, just by adding a new theme bundle.

## Channel 1 — Ambient music bed

- A looping ambient bed, always playing, sets overall mood.
- **Generated by Tone.js by default — no recording.** Each theme defines a
  **fixed chord progression**; the generator randomizes voicing, register,
  and note timing over a pad or plucked instrument. Fixing the progression
  per theme is the deliberate mitigation for generative ambient's known
  failure mode: wandering aimlessly and turning monotonous. The randomness
  lives in the surface, not the harmony.
- **Two layers, because "always playing" is a requirement and not a
  description.** The first implementation sampled one note at a time from
  the current chord with silence between, and it did not read as music —
  it read as a trickle of unrelated plinks, the progression was never
  actually sounded, and chord changes landed in gaps where nobody could
  hear them. Continuity is a texture problem, not a mixing one; no amount
  of reverb fills a hole. So:
  - **A drone** holds the current chord's root and fifth indefinitely,
    with a multi-second attack and a longer release, so something is
    always sounding. Chord changes crossfade because the outgoing
    release outlasts the incoming attack, and a pitch common to both
    chords is **held rather than retriggered** — a pedal tone, and the
    strongest continuity cue available. It omits the third, so the
    harmony can move without the foundation feeling stuck.
  - **A sparse surface** of two chord tones at a time on the themed
    instrument, each gesture held *longer than the gap that follows it*
    so consecutive gestures overlap into one line.
- **`droneLevel` is the continuity knob.** At 0 there is no drone and the
  bed reverts to the trickle described above. `noteOverlap` above 1
  guarantees the surface never breaks. Both are theme parameters.
- **A theme supplying `bed.pulse` gets a metered engine instead**, because
  ambient cannot be *cheerful* at any parameter setting. Cheerfulness in
  game music is made of meter, and "randomize the timing of single notes"
  cannot express meter. Metered mode is three layers over the same fixed
  progression:
  - a **bass** figure per eighth note, written as chord degrees with rests,
    alternating root and fifth so the line walks rather than sits;
  - **chord stabs** on the off-beats, against the bass's on-beats. This
    oom-pah carries more of the feeling than every other parameter
    combined, which is why a test asserts the two patterns never collide;
  - a **melody** on a syncopated sixteenth grid, whose contour is generated
    once from the seed and then repeated, remapped onto whichever chord is
    current. Repetition is what makes a melody recognisable; the remapping
    is what keeps it in key while the harmony moves. Every pitch is a chord
    degree, so a generated line is in key by construction, not by luck.

  Plus `swing`, which is the cheapest cheerfulness lever there is — a
  straight grid reads as mechanical however bright the timbre. The three
  layers are spread across roughly three octaves; bunching them turns the
  texture to mud.

  In metered mode `droneLevel` wants to be **low**: the pulse is already
  carrying continuity, and a prominent drone only muddies it.
- **The grooves are data, not code paths.** Patterns are step arrays in
  `audioThemes/index.ts`, so a new groove is more numbers — the same
  themes-as-parameters payoff the visuals get. Nothing branches on theme id.
- Scheduling runs on `Tone.Transport`, not `setTimeout`: sample-accurate
  rather than drifting, and it isn't throttled into stuttering when the
  tab loses focus. Channels 2 and 3 schedule off `Tone.now()` and never
  read the transport position, so starting and stopping it for the bed is
  safe.
- Reverb/delay send levels are theme parameters — ambience does more for
  perceived mood than note choice does.
- **The bed also plays behind the title screen**, alone: there is nothing
  to sonify behind a menu, so channels 2 and 3 are not constructed there.
  It starts on the first click or keypress, since browsers refuse to start
  an audio context before a gesture.
- Volume slider and mute toggle as usual, and **live**: the mix applies to
  whatever is already playing rather than waiting for a commit. A volume
  control that needs an OK press is a broken volume control — the only way
  anyone sets a level is by listening while they move it. Muted means
  exactly zero gain, not a very quiet signal.
- Stretch goal (not initial scope): shift to a tenser voicing or a minor
  substitution *within* a theme based on drawdown state. Much cheaper now
  that the bed is synthesized rather than a fixed recording — but don't
  build it until channels 2/3 feel right.

### Composed tracks from MIDI

A third bed mode, alongside ambient and metered: when a theme ships
`public/midi/<id>.mid`, that file **replaces** the generated bed. `createTrackBed`
satisfies the same `AmbientBed` interface as `createAmbientBed`, so pause, the music
bus and the live mix are unchanged and nothing downstream knows which is playing. A
theme with no file, or a file that fails to load, falls back to the generated bed.

**MIDI is notes, not sound.** A `.mid` carries no audio, so it replaces only the part
of the bed that decides *which notes to play*. There is no General MIDI soundfont
here — adding one would mean shipping samples — so the voices are this player's own
choice and a track will not sound the way it does in a DAW. That is the accepted cost.

Voices come from the file's **program changes**, mapped to twelve synth recipes by
General MIDI instrument family — a program number selects a recipe rather than a patch,
which is a weaker claim than GM makes and far better than ignoring it. The first version
assigned voices by *channel index* instead, which made a bass part and a string part
identical whenever they sat next to each other, throwing away the one piece of
instrumentation the file states. Recipes differ in envelope as much as waveform: a piano
and an organ on the same triangle wave are told apart by attack and sustain. Voices are
keyed by `channel:program` and built lazily, so a program change mid-track gets its own
voice and a three-track file makes three.

Percussion (channel 10, zero-based 9) uses the **General MIDI drum map** — kick, snare,
rim, clap, closed and open hat, ride, toms, cowbell — each a blend of filtered noise and
a pitched `MembraneSynth`, since most drums are both. This replaced a split on
`note < 45` that gave every cymbal, clap and cowbell the same white noise.

**Controller data is honoured**, which is most of what makes an arrangement sound
arranged: CC 7 (channel volume) and CC 11 (expression) scale each note's velocity, CC 10
sets pan, and CC 120/123 release held notes. Skipping them plays every part at the level
of the loudest thing in the file. Channel volume defaults to 100 rather than 127, per GM,
so a file that never sets it does not come out louder than one that does.

A **compressor** sits before the music bus. Ten voices whose peaks coincide clip where
four never would, and a fixed trim can only trade headroom against being inaudible.

The bed is trimmed **-12 dB** relative to the generated one. A composed arrangement is
many simultaneous voices where the generated bed is two to four, so at equal bus gain it
arrives far louder; the trim is what keeps the player's music slider covering the same
usable range whichever bed is playing.

**Served, not baked.** The files live in `public/midi/` and are fetched when a run
starts. Baking them into `content/` as note arrays was the first plan and measured
worse on every axis: 3× larger gzipped (58 kB against 19 kB for the five placeholder
tracks) and 261 kB of generated TypeScript committed to the repo. MIDI is binary and
delta-encoded — about five bytes a note against ~25 for any JSON shape — so converting
it away from its own format only makes it bigger. Cache headers are in
`staticwebapp.config.json`; one hour with revalidation, since a recomposed track reuses
its filename.

The decoder is `data/midi.ts`, hand-rolled rather than `@tonejs/midi` for the same
reason the PRNG and the noise generators are: it needs one function's worth of the
format, and as a pure bytes-to-events transform it is directly testable. It resolves
the **tempo map at decode time**, so every note carries an absolute time in seconds and
the scheduler never sets a transport tempo — a file with sixty-two tempo changes needs
no handling at playback.

Decoding is **two passes**: reading happens per track, interpretation cannot. A format 1
file keeps its tempo map in track 0 and its notes elsewhere, and a controller change for
one channel may be written in a different track from the notes it governs. So pass one
collects raw events with ticks, pass two sorts them into a single timeline and walks it
carrying tempo and per-channel state. Interpreting track by track was the first shape and
was wrong in a way nothing failed on — notes came out at plausible times with the wrong
mix. Skipped: pitch bend, aftertouch, other controllers, sysex, and every meta event
except tempo and end-of-track.

Loading happens in `app/runSession.ts`, not in the audio system: `src/audio` may not
import `@data` (see `eslint.zones.js`), so the composition root fetches and hands over
the notes. That keeps the zone table and `architecture.test.ts` untouched.

Two consequences worth knowing. The loop point is the file's **end-of-track marker**,
falling back to the last note's end when that comes earlier — not a bar line, and not the
last note. Trailing silence is musical: a sequence that rests two bars before repeating
says so with a late end-of-track tick, and looping at the last note cuts the rest and
brings the repeat back early. That was a real bug in the first version. And a composed track ignores `worldSeed`, so "New world" restyles
the visuals and leaves the music identical; that is the point of composing, but it makes
the seed a visuals-only control for those themes.

## Channel 2 — Movement sonification (the "up/down" tones)

This is the piece that makes price movement audible on every jump:

- For each pole-to-pole jump, compute the price delta to the next pole.
- Map **direction** → pitch step direction (up move = step up, down move =
  step down).
- Map **magnitude** → interval size (bigger move = bigger jump in pitch).
- Quantize into a **scale** — *which* scale and *which* instrument/timbre
  are theme properties (e.g. major pentatonic + bells for a jolly theme,
  minor pentatonic + cello for a serious one). Any scale choice keeps the
  result from ever sounding dissonant, regardless of what the underlying
  price data does — themes only change the flavor, not this guarantee.

## Channel 3 — Event stingers (one-shots)

Stingers are keyed to **semantic position events, not button names.** This
distinction is load-bearing: when short, the *closing* action is `buy`, so a
stinger named `sellProfit` fired on the sell button would misfire on every
short exit — playing an exit sound on entry and vice versa.

Six events, each theme-supplied. This table is the canonical stinger list,
but it is **not** the full engine event vocabulary — `engine/output/`
([code-structure.md](./code-structure.md#src)) also emits events audio
doesn't consume (unit added/removed for the ghost stack, streak change,
advisory breach, bar advanced). Don't treat this list as complete for
non-audio consumers.

| Event | Fires when |
|---|---|
| `positionOpened` | Size moves off zero, either direction |
| `positionIncreased` | Size grows in the direction already held (scaling in) |
| `positionClosed.profit` | Any size reduction realizing positive P&L |
| `positionClosed.loss` | Any size reduction realizing negative P&L |
| `stoppedOut` | A stop plugin auto-closed the position ([stops.md](./stops.md)) |
| `actionDenied` | A press that couldn't be honoured — sell while flat with shorting off, or entry with no buying power |

- **`stoppedOut` must be deliberately different from
  `positionClosed.loss` in every theme.** A triggered stop should *feel*
  different from a deliberate exit, not just look different in a log — that
  distinction is the whole point of the discipline lesson, so a theme's
  stop-out cue should read as clearly more jarring than its own manual-loss
  cue whatever its overall tone.
- **`actionDenied`** exists so a rejected press never reads as a dropped
  input. It should be short, dry, and unmistakably *not* a trade sound —
  a soft thud rather than anything melodic, so it can't be confused with a
  fill. Required in every theme.

## Audio themes

A theme defines content for **all three channels at once**, so switching
mood never leaves channels mismatched (e.g. a jolly ambient bed paired with
a harsh trading-floor stinger set).

Because everything is synthesized ([procedural-assets.md](./procedural-assets.md)),
a theme is a **parameter set** — no recorded audio at
all. Conceptually:

```
AudioTheme {
  id, displayName
  bed: {                                       // channel 1, generative
    progression: [chord, chord, ...],          // fixed per theme
    instrument, register, noteRateRange,
    reverbSend, delaySend,
  }
  sonification: { scale, instrument }          // channel 2
  stingers: {                                  // channel 3, synth recipes
    positionOpened, positionIncreased,
    positionClosedProfit, positionClosedLoss,
    stoppedOut, actionDenied,
  }
}
```

Playback code always asks "what does the *current* theme supply for
channel N" — it never branches on theme id. Adding a new theme (e.g.
`chill`, `arcade`) is a new plain data object, no engine changes and no
audio production.

Volume/mute controls (`audio.masterVolume`, `audio.musicVolume`,
`audio.sfxVolume`, and their mute toggles) sit on top of whichever theme
is active — they're mixing knobs, not theme properties.

### Initial theme set

These describe *parameter intent*; exact synth recipes are tuned in code.

| | **Jolly** | **Serious** |
|---|---|---|
| Bed progression | Major, bright (e.g. I–V–vi–IV) | Minor, unresolved (e.g. i–VI–III–VII) |
| Bed instrument | Plucked/marimba-like synth | Slow low pad |
| Sonification scale | Major pentatonic | Minor pentatonic (or dorian) |
| Sonification instrument | Bright bell/xylophone synth | Cello-ish or piano-ish synth |
| Buy stinger | Cartoonish coin/chime | Subdued click |
| Sell-in-profit stinger | Triumphant arpeggio | Understated resolving chime |
| Sell-at-a-loss stinger | Comedic descending slide | Low descending tone |
| Stop-out alarm | Playful "uh-oh" cue — still clearly worse than the loss stinger above | Sharp buzzer/siren — clearly worse than the loss stinger above |
| Denied cue | Muted rubbery thud | Dry short click, lower than the entry click |
| Reverb/delay | Light, dry | Heavier, more spacious |

**Default: `jolly`**, for approachability on first launch. The settings UI
pairs this with the matching visual theme under one "mood" picker — see
[visuals.md](./visuals.md#visual-themes). Additional themes (`chill`,
`arcade`, etc.) can be added the same way once these two are validated.

## Library choice

Use **Tone.js** for all three channels — it's the whole audio
implementation, not a helper. It has built-in scale/note quantization and
precise scheduling, which is exactly what channel 2 needs (turning a price
delta into "the nearest note in the current theme's scale") without
hand-rolling that math, plus the synths, effects sends, and transport
scheduling that channels 1 and 3 need. Raw Web Audio would mean rebuilding
all of that; a sample-playback library like Howler solves a problem this
project doesn't have, since there are no samples.

## Config

- `audio.theme` — selects the active theme bundle (see above).
- Master volume, music volume, SFX volume — each with a mute toggle,
  theme-independent.
- See [config.md](./config.md) for the full key reference.

## Sequencing note

Build this **after** the core trading loop (state machine, sizing, risk
management) feels right — audio is easy to get wrong stylistically while
the underlying mechanics are still being tuned, and it has zero coupling to
game logic so it's safe to bolt on later. Build one theme (`jolly` or
`serious`) end-to-end first; adding the second is then just filling in the
bundle, not new engine work.
