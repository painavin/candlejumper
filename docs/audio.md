# Audio Design

## Approach

The ask was music/sound "tied to up/down" price movement. Full adaptive
music generation is a rabbit hole — instead, use **sonification**: map data
to simple musical events layered over a static ambient bed. Three
independent channels, each with its own volume/mute config.

Each channel's *mechanism* (how it works) is fixed by the engine. Its
*content* (which loop, which scale, which stinger sounds) is supplied by
the currently selected **audio theme** — see [Audio themes](#audio-themes)
below — so the game can ship multiple moods (jolly, serious, ...) without
touching channel logic, just by adding a new theme bundle.

## Channel 1 — Ambient music bed

- A looping ambient bed, always playing, sets overall mood.
- **Fully generated by Tone.js — no audio files.** Each theme defines a
  **fixed chord progression**; the generator randomizes voicing, register,
  and note timing over a pad or plucked instrument. Fixing the progression
  per theme is the deliberate mitigation for generative ambient's known
  failure mode: wandering aimlessly and turning monotonous. The randomness
  lives in the surface, not the harmony.
- Reverb/delay send levels are theme parameters — ambience does more for
  perceived mood than note choice does.
- Volume slider and mute toggle as usual.
- Stretch goal (not initial scope): shift to a tenser voicing or a minor
  substitution *within* a theme based on drawdown state. Much cheaper now
  that the bed is synthesized rather than a fixed recording — but don't
  build it until channels 2/3 feel right.

## Channel 2 — Movement sonification (the "up/down" tones)

This is the piece that makes price movement audible on every jump:

- For each pole-to-pole jump, compute the price delta to the next pole.
- Map **direction** → pitch step direction (up move = step up, down move =
  step down).
- Map **magnitude** → interval size (bigger move = bigger jump in pitch).
- Quantize into a **scale** — *which* scale and *which* instrument/timbre
  are theme properties (e.g. major pentatonic + bells for a jolly theme,
  minor pentatonic + cello for a serious one). Any scale choice keeps the
  result from ever sounding dissonant, regardless of what the underlying
  price data does — themes only change the flavor, not this guarantee.

## Channel 3 — Event stingers (one-shots)

Stingers are keyed to **semantic position events, not button names.** This
distinction is load-bearing: when short, the *closing* action is `buy`, so a
stinger named `sellProfit` fired on the sell button would misfire on every
short exit — playing an exit sound on entry and vice versa.

Five events, each theme-supplied:

| Event | Fires when |
|---|---|
| `positionOpened` | Size moves off zero, either direction |
| `positionIncreased` | Size grows in the direction already held (scaling in) |
| `positionClosed.profit` | Any size reduction realizing positive P&L |
| `positionClosed.loss` | Any size reduction realizing negative P&L |
| `stoppedOut` | A stop plugin auto-closed the position ([stops.md](./stops.md)) |
| `actionDenied` | A press that couldn't be honoured — sell while flat with shorting off, or entry with no buying power |

- **`stoppedOut` must be deliberately different from
  `positionClosed.loss` in every theme.** A triggered stop should *feel*
  different from a deliberate exit, not just look different in a log — that
  distinction is the whole point of the discipline lesson, so a theme's
  stop-out cue should read as clearly more jarring than its own manual-loss
  cue whatever its overall tone.
- **`actionDenied`** exists so a rejected press never reads as a dropped
  input. It should be short, dry, and unmistakably *not* a trade sound —
  a soft thud rather than anything melodic, so it can't be confused with a
  fill. Required in every theme.

## Audio themes

A theme defines content for **all three channels at once**, so switching
mood never leaves channels mismatched (e.g. a jolly ambient bed paired with
a harsh trading-floor stinger set).

Because everything is synthesized ([procedural-assets.md](./procedural-assets.md)),
a theme is a **parameter set, not an asset bundle** — no audio files at
all. Conceptually:

```
AudioTheme {
  id, displayName
  bed: {                                       // channel 1, generative
    progression: [chord, chord, ...],          // fixed per theme
    instrument, register, noteRateRange,
    reverbSend, delaySend,
  }
  sonification: { scale, instrument }          // channel 2
  stingers: {                                  // channel 3, synth recipes
    positionOpened, positionIncreased,
    positionClosedProfit, positionClosedLoss,
    stoppedOut, actionDenied,
  }
}
```

Playback code always asks "what does the *current* theme supply for
channel N" — it never branches on theme id. Adding a new theme (e.g.
`chill`, `arcade`) is a new plain data object, no engine changes and no
audio production.

Volume/mute controls (`audio.masterVolume`, `audio.musicVolume`,
`audio.sfxVolume`, and their mute toggles) sit on top of whichever theme
is active — they're mixing knobs, not theme properties.

### Initial theme set

These describe *parameter intent*; exact synth recipes are tuned in code.

| | **Jolly** | **Serious** |
|---|---|---|
| Bed progression | Major, bright (e.g. I–V–vi–IV) | Minor, unresolved (e.g. i–VI–III–VII) |
| Bed instrument | Plucked/marimba-like synth | Slow low pad |
| Sonification scale | Major pentatonic | Minor pentatonic (or dorian) |
| Sonification instrument | Bright bell/xylophone synth | Cello-ish or piano-ish synth |
| Buy stinger | Cartoonish coin/chime | Subdued click |
| Sell-in-profit stinger | Triumphant arpeggio | Understated resolving chime |
| Sell-at-a-loss stinger | Comedic descending slide | Low descending tone |
| Stop-out alarm | Playful "uh-oh" cue — still clearly worse than the loss stinger above | Sharp buzzer/siren — clearly worse than the loss stinger above |
| Denied cue | Muted rubbery thud | Dry short click, lower than the entry click |
| Reverb/delay | Light, dry | Heavier, more spacious |

**Default: `jolly`**, for approachability on first launch. The settings UI
pairs this with the matching visual theme under one "mood" picker — see
[visuals.md](./visuals.md#visual-themes). Additional themes (`chill`,
`arcade`, etc.) can be added the same way once these two are validated.

## Library choice

Use **Tone.js** for all three channels — it's the whole audio
implementation, not a helper. It has built-in scale/note quantization and
precise scheduling, which is exactly what channel 2 needs (turning a price
delta into "the nearest note in the current theme's scale") without
hand-rolling that math, plus the synths, effects sends, and transport
scheduling that channels 1 and 3 need. Raw Web Audio would mean rebuilding
all of that; a sample-playback library like Howler solves a problem this
project doesn't have, since there are no samples.

## Config

- `audio.theme` — selects the active theme bundle (see above).
- Master volume, music volume, SFX volume — each with a mute toggle,
  theme-independent.
- See [config.md](./config.md) for the full key reference.

## Sequencing note

Build this **after** the core trading loop (state machine, sizing, risk
management) feels right — audio is easy to get wrong stylistically while
the underlying mechanics are still being tuned, and it has zero coupling to
game logic so it's safe to bolt on later. Build one theme (`jolly` or
`serious`) end-to-end first; adding the second is then just filling in the
bundle, not new engine work.
